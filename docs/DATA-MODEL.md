# Проект физической модели хранения

- **Версия:** 0.1
- **Дата:** 2026-11-24
- **Статус:** первичный DDL реализован в SchemaInstaller; требуется проверка на целевой версии Битрикс и MySQL.
- **Назначение:** определить минимальную структуру хранения, индексы, ограничения объёма и правила очистки.

## 1. Принципы

1. Хранилище рассчитано на частую вставку и чтение журнала с фильтрами.
2. Основные поля события доступны без чтения payload.
3. Данные запроса/ответа отделены от основной записи и могут отсутствовать.
4. Справочник источников не является обязательной зависимостью события.
5. Не использовать обязательные внешние ключи между таблицами на первом этапе: удаление по retention должно оставаться контролируемым и пакетным, а установка — переносимой.
6. Временные поля хранятся в UTC.
7. Секреты маскируются до записи. База не должна быть первым местом, где обнаруживается необходимость маскирования.
8. Схема не должна хранить PHP-сериализацию и произвольные бинарные объекты.

## 2. Таблицы

Предварительные имена:

- `b_cmi_event` — основная запись события;
- `b_cmi_event_data` — дополнительные метаданные и разрешённые payload;
- `b_cmi_source` — необязательные описания источников.

### 2.1. b_cmi_event

| Поле | Предлагаемый тип MySQL | Назначение |
|---|---|---|
| EVENT_ID | CHAR(36) ASCII, PK | UUID v4 события |
| SOURCE_CODE | VARCHAR(64) | Код источника, всегда хранится непосредственно в событии |
| OPERATION | VARCHAR(128) | Код операции |
| DIRECTION | VARCHAR(12) | incoming / outgoing / internal |
| STATUS | VARCHAR(12) | pending / success / error |
| CORRELATION_ID | VARCHAR(128), NULL | Внешний идентификатор группы |
| PARENT_EVENT_ID | CHAR(36) ASCII, NULL | Родительское событие без FK |
| DATE_START | DATETIME | Время начала регистрации в UTC |
| OCCURRED_AT | DATETIME, NULL | Необязательное время события, переданное вызывающим кодом; не заменяет DATE_START |
| DATE_FINISH | DATETIME, NULL | Время завершения в UTC |
| DURATION_MS | BIGINT UNSIGNED, NULL | Длительность в миллисекундах |
| HTTP_STATUS | SMALLINT UNSIGNED, NULL | HTTP-статус, если применимо |
| RESULT_CODE | VARCHAR(64), NULL | Краткий код результата |
| ERROR_CLASS | VARCHAR(255), NULL | Класс исключения |
| ERROR_CODE | VARCHAR(64), NULL | Безопасный код исключения |
| ERROR_MESSAGE | VARCHAR(1000), NULL | Ограниченное и очищенное сообщение |
| ERROR_FILE | VARCHAR(500), NULL | Файл, если разрешено настройками |
| ERROR_LINE | INT UNSIGNED, NULL | Строка, если разрешено настройками |

Типы и размеры предварительные. Первичный DDL создан в `lib/Storage/SchemaInstaller.php`; имена и типы ещё должны быть проверены на целевой BitrixVM. ORM-классы пока не реализованы.

### 2.2. b_cmi_event_data

| Поле | Предлагаемый тип MySQL | Назначение |
|---|---|---|
| EVENT_ID | CHAR(36) ASCII, PK | ID события |
| REQUEST_META | MEDIUMTEXT, NULL | JSON безопасных метаданных запроса |
| RESPONSE_META | MEDIUMTEXT, NULL | JSON безопасных метаданных ответа |
| CONTEXT | MEDIUMTEXT, NULL | JSON дополнительного технического контекста |
| REQUEST_PAYLOAD | MEDIUMTEXT, NULL | Явно разрешённое текстовое тело запроса |
| RESPONSE_PAYLOAD | MEDIUMTEXT, NULL | Явно разрешённое текстовое тело ответа |
| ERROR_TRACE | MEDIUMTEXT, NULL | Stack trace, только если отдельно включён |

Отдельная запись создаётся только если есть дополнительные данные. Payload — UTF-8 текст или JSON-представление поддерживаемой структуры; бинарные файлы и PHP-объекты не поддерживаются.

### 2.3. b_cmi_source

| Поле | Предлагаемый тип MySQL | Назначение |
|---|---|---|
| CODE | VARCHAR(64), PK | Стабильный код источника |
| NAME | VARCHAR(255) | Отображаемое имя |
| DESCRIPTION | VARCHAR(1000), NULL | Описание |
| DATE_CREATE | DATETIME | Дата создания в UTC |
| DATE_UPDATE | DATETIME | Дата изменения в UTC |

Отсутствие строки в этой таблице не запрещает запись события. Удаление описания источника не удаляет события.

## 3. Индексы

Для `b_cmi_event`:

| Индекс | Поля | Для чего |
|---|---|---|
| PRIMARY | EVENT_ID | Карточка события |
| IX_CMI_EVENT_DATE | DATE_START | Список по периоду и очистка |
| IX_CMI_EVENT_SOURCE_DATE | SOURCE_CODE, DATE_START | Фильтр по источнику и периоду |
| IX_CMI_EVENT_STATUS_DATE | STATUS, DATE_START | Фильтр по статусу и периоду |
| IX_CMI_EVENT_DIRECTION_DATE | DIRECTION, DATE_START | Фильтр по направлению и периоду |
| IX_CMI_EVENT_CORRELATION | CORRELATION_ID | Поиск связанной цепочки |

Для `b_cmi_event_data` достаточно первичного ключа `EVENT_ID`. Для `b_cmi_source` первичный ключ `CODE` уже обеспечивает поиск по коду. Справочник содержит только описательные сведения и не отключает приём событий.

Не индексировать длинные тексты, payload, сообщения исключений и stack trace. Индексы должны быть подтверждены EXPLAIN на тестовых объёмах.

## 4. Ограничения объёма

Предлагаемые стартовые лимиты MVP:

- sourceCode: до 64 символов;
- operation: до 128 символов;
- correlationId: до 128 символов;
- parentEventId: до 36 символов для UUID v4;
- request metadata: до 16 KiB;
- response metadata: до 16 KiB;
- context: до 8 KiB;
- каждый request/response payload: до 64 KiB;
- stack trace: выключен по умолчанию, при включении — до 32 KiB;
- общий дополнительный объём на событие: не более 128 KiB.

Лимиты применяются до сериализации/глубокой обработки и повторно после Sanitizer. Значения — стартовое предложение; они должны быть подтверждены тестом и настройками MVP. Не допускать, чтобы одна запись могла занять мегабайты без явного решения администратора.

## 5. Жизненный цикл и атомарность

- Начало события создаёт строку `pending`.
- Финализация выполняет условное обновление только для `STATUS = pending`.
- Если обновлено 0 строк, повторная финализация возвращает `already_finalized` либо `not_recorded`.
- Данные результата записываются только в рамках успешной финализации.
- Ошибка записи payload не должна приводить к перезаписи/потере исходного статуса события; точная стратегия частичного сохранения должна быть проверена тестами.
- Не выполнять очистку и тяжёлые выборки в пути begin/succeed/fail.

Запись через default connection может участвовать во внешней транзакции приложения и исчезнуть при rollback. Опциональный независимый режим описан в [TRANSACTION-STRATEGY.md](TRANSACTION-STRATEGY.md): отдельное именованное соединение к той же БД, настроенное администратором. Не считать его рабочим до прохождения теста на минимальной целевой версии ядра. При включённом независимом режиме запрещён незаметный fallback на default connection.

## 6. Очистка и retention

Предлагаемая политика MVP:

- настраиваемый срок хранения событий; стартовое значение — 30 дней;
- очистка выполняется пакетами, например до 500–1000 событий за запуск;
- выборка на удаление использует индекс `DATE_START`;
- сначала удаляются данные из `b_cmi_event_data` для выбранного пакета ID, затем записи из `b_cmi_event`;
- очистка запускается агентом/cron вне синхронного запроса интеграции;
- повторный запуск безопасен;
- при ошибке одного пакета следующий запуск продолжает очистку;
- события старше retention не должны удаляться из-за ошибки часового пояса или некорректного параметра.

Реализация: агент `EventCleanup::run()` запускается ежедневно; срок задаётся опцией модуля `retention_days` (по умолчанию 30 дней, допустимый диапазон 1–3650). Для изменения значения используется `Bitrix\\Main\\Config\\Option::set('codematrix.integrationinspector', 'retention_days', '90')`. Агент выбирает не более 500 ID за итерацию по индексу `DATE_START`, удаляет связанные строки `b_cmi_event_data`, затем события. Параллельный запуск защищён MySQL advisory lock `GET_LOCK`; при занятой блокировке агент переносит работу на следующий запуск. Ошибка записывается в PHP error log через `AddMessage2Log`, следующий запуск продолжит очистку.

## 7. Удаление модуля

Нужно разделить два сценария:

1. **Обычное удаление модуля:** по умолчанию предложить сохранить диагностические таблицы/данные, чтобы администратор случайно не потерял историю.
2. **Полное удаление данных:** отдельное явное подтверждение с предупреждением о необратимости.

Конкретный UX установщика/деинсталлятора и штатный способ выбора необходимо проверить на целевой версии Битрикс.

## 8. ORM и установка

Официальная документация Битрикс описывает DataManager как базовый класс для доступа к таблицам и требует реализации `getTableName()` и `getMap()`. В учебном материале по ORM используются типы полей, включая IntegerField, StringField и DatetimeField.

До реализации проверить:

- наличие нужных типов полей в минимальной версии ядра;
- соответствие ORM типов физическим BIGINT/SMALLINT/TEXT полям;
- корректность UUID-строк и nullable полей;
- создание индексов через выбранный механизм установки;
- обновление схемы без потери данных;
- поведение при повторной установке/обновлении;
- MySQL strict mode и utf8mb4.

## 9. Обязательные проверки до утверждения схемы

1. Проверить SQL DDL на минимальной целевой версии MySQL.
2. Проверить ORM map для всех типов колонок.
3. Проверить атомарную финализацию двумя параллельными процессами.
4. Проверить очистку больших пакетов и отсутствие orphan data.
5. Проверить вставку при активной транзакции бизнес-кода.
6. Проверить поведение при частичном отказе записи event_data.
7. Проверить EXPLAIN для основных фильтров на тестовом объёме.
8. Проверить реальный размер индексов и рост таблиц.
9. Проверить деинсталляцию с сохранением и полным удалением данных.

До прохождения проверок схема остаётся предварительной реализацией, а не подтверждённым контрактом для всех поддерживаемых окружений.
