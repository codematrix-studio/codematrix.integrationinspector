# Публичный API (проект спецификации)

- **Версия:** 0.1
- **Дата:** 2026-11-24
- **Статус:** проектное предложение; контракт не утверждён и не реализован.
- **Назначение:** зафиксировать стабильный внешний интерфейс до разработки ядра.

## 1. Принципы контракта

1. Интеграция сама выполняет бизнес-операцию; Inspector только регистрирует её ход и результат.
2. Запись диагностических данных не должна менять результат основной операции.
3. Сбор данных явный: только переданные вызывающим кодом значения и контекст адаптера.
4. По умолчанию сохраняются метаданные; тела запросов/ответов не записываются, пока это явно не разрешено настройками.
5. Публичный API не раскрывает ORM, таблицы, административные классы и детали хранилища.
6. API должен допускать работу без HTTP: CLI, агенты, cron, очереди и фоновые обработчики.
7. Контракт не обещает автоматический перехват сетевого трафика.

## 2. Предлагаемый публичный фасад

Namespace: `CodeMatrix\IntegrationInspector\Api`

Предлагаемые публичные типы:
- `Inspector` — статический фасад;
- `EventInput` — неизменяемое описание запускаемой операции;
- `EventHandle` — дескриптор начатого события;
- `EventOutcome` — данные результата;
- `SourceDefinition` — описание источника;
- `SourceReference` — ссылка на зарегистрированный источник;
- `EventStartResult` / `EventFinalizeResult` — результат попытки регистрации/завершения.

Предлагаемые методы фасада:

```php
Inspector::registerSource(SourceDefinition $source): SourceReference;

Inspector::begin(EventInput $input): EventStartResult;

Inspector::isEnabled(): bool;
```

Методы завершения принадлежат дескриптору:

```php
$start = Inspector::begin($input);

if ($start->isRecorded()) {
    $event = $start->event();

    try {
        // Вызов внешней системы или обработка входящего запроса.
        $outcome = $integration->execute();

        $event->succeed(EventOutcome::fromArray([
            'http_status' => 200,
            'response' => $safeResponseMetadata,
        ]));
    } catch (\Throwable $exception) {
        $event->fail($exception);
        throw $exception;
    }
}
```

Пример иллюстрирует предполагаемый стиль API. Названия классов, методы и сигнатуры остаются предложением до утверждения.

## 3. Источник интеграции

Источник — стабильная логическая система или канал, например `1c`, `crm`, `delivery`, `payment`, `custom_api`.

`SourceDefinition`:
- `code` — обязательный стабильный машинный код, lowercase ASCII, цифры, точка, дефис и подчёркивание; рекомендуемый формат slug;
- `name` — обязательное отображаемое имя;
- `description` — необязательное описание;
- `enabled` — признак разрешения регистрации событий от источника.

Регистрация по одному `code` идемпотентна: повторная регистрация обновляет допустимые описательные поля, но не создаёт дубликат источника. Конфликт с несовместимым определением должен возвращаться как диагностический результат, а не менять чужую запись молча.

Удаление источника не должно каскадно удалять историю событий. Для MVP достаточно отключения источника; физическое удаление и политика архивирования требуют отдельного решения.

## 4. Входные данные события

`EventInput` содержит:

| Поле | Требование | Назначение |
|---|---|---|
| `source` | обязательно | `SourceReference` либо стабильный code зарегистрированного источника |
| `operation` | обязательно | машинный код операции, например `order.export` |
| `direction` | обязательно | `incoming`, `outgoing` или `internal` |
| `correlationId` | необязательно | связывает несколько событий одной бизнес-операции |
| `parentEventId` | необязательно | идентификатор непосредственного родительского события |
| `request` | необязательно | структурированные метаданные запроса |
| `context` | необязательно | дополнительные скалярные/структурированные метаданные |
| `occurredAt` | необязательно | время события, если оно известно вызывающему коду |

Ограничения:
- `source` и `operation` не могут быть пустыми;
- длины строк и глубина/размер структур должны быть ограничены конфигурацией;
- произвольные объекты, ресурсы, замыкания и сериализация PHP-объектов не поддерживаются;
- секреты должны быть отфильтрованы до постоянной записи;
- передача тела запроса — отдельная явная операция, не часть автоматического сбора.

## 5. Идентификаторы и корреляция

- Каждое событие получает уникальный `eventId`, генерируемый модулем.
- `correlationId` объединяет несколько событий, относящихся к одной бизнес-операции. Если вызывающий код его не передал, модуль может создать новый ID для данного события; автоматическое объединение соседних событий не выполняется.
- `parentEventId` указывает на родительское событие, если вызывающий код явно передал его.
- Значения correlation/parent не являются механизмом авторизации и не должны приниматься как доверенные данные.
- Формат идентификатора (UUIDv4/UUIDv7/другой) требует финального выбора при проектировании хранения и требований к индексам.

## 6. Жизненный цикл

Предлагаемые состояния:
- `pending` — событие зарегистрировано, операция ещё выполняется;
- `success` — вызывающий код сообщил об успешном завершении;
- `error` — вызывающий код сообщил об ошибке.

Допустимые переходы:

```text
begin -> pending
pending -> success
pending -> error
```

Повторная финализация запрещена. Вызов `succeed()` или `fail()` после финального состояния возвращает результат `already_finalized` и не перезаписывает первоначальный результат. Состояния `abandoned`, `cancelled` и автоматическое определение зависших событий не входят в контракт MVP.

Если запись `pending` не удалась, дескриптор всё равно должен позволять бизнес-коду продолжить операцию в безопасном режиме; финализация возвращает соответствующий диагностический статус.

## 7. Результат и ошибка

`EventOutcome` может содержать:
- HTTP-статус;
- структурированные метаданные ответа;
- длительность/время завершения, если измерены вызывающим кодом или модулем;
- краткий код результата;
- безопасный контекст.

Модуль должен измерять длительность монотонными часами от начала события до финализации. Время календарных часов хранится отдельно для отображения.

`fail(Throwable $exception)` фиксирует безопасный снимок ошибки:
- класс исключения;
- сообщение после ограничения длины и санитарной обработки;
- код исключения;
- файл и строка (если разрешено настройками);
- stack trace — выключен по умолчанию либо хранится только при отдельном явном разрешении и ограничении размера.

Не сериализовать объект исключения целиком. Не сохранять аргументы функций, локальные переменные и произвольные свойства объектов.

Повторное выбрасывание исходного исключения остаётся обязанностью интеграционного кода. Inspector не должен поглощать бизнес-исключение.

## 8. HTTP-данные и payload

HTTP — необязательный контекст, а не обязательная зависимость ядра. Предлагаемая структура запроса/ответа:
- метод;
- URL без userinfo и с удалением/маскированием чувствительных query-параметров;
- заголовки после allowlist/denylist sanitization;
- HTTP status;
- размер тела;
- тело только при включённой настройке и явной передаче.

По умолчанию:
- тела не сохраняются;
- заголовки и query-параметры проходят маскирование;
- Authorization, Proxy-Authorization, Cookie, Set-Cookie и ключи, похожие на password/token/secret/api_key, маскируются;
- действует лимит размера до сериализации и после sanitization;
- неподдерживаемые типы данных отбрасываются с диагностическим признаком.

Sanitizer должен работать до записи. В UI не допускается повторная обработка уже сохранённого секрета как замена санитаризации на входе.

## 9. Ошибки самого Inspector

Рекомендуемая политика MVP — best effort:
- ошибки Inspector не выбрасываются в основной поток бизнес-операции;
- результат API явно сообщает `recorded`, `disabled`, `storage_unavailable`, `invalid_input` или иной ограниченный код;
- диагностическая ошибка Inspector не должна логироваться через тот же Inspector (защита от рекурсии);
- нельзя гарантировать сохранение события при отказе БД;
- не выполнять скрытые сетевые обращения и повторные попытки интеграционного запроса.

Строгий режим, в котором ошибка диагностической записи может быть выброшена вызывающему коду, не включать в MVP без отдельного обоснования и явного решения.

## 10. Асинхронные и длительные операции

Для операций в одном PHP-процессе `EventHandle` остаётся в памяти до финализации.

Передача handle между процессами, сериализация объекта, продолжение события в другом worker и восстановление pending-события по токену не входят в MVP. Для очередей и cron вызывающий код может создать отдельное событие в каждом процессе и связать их общим `correlationId` и, при наличии, `parentEventId`.

## 11. Транзакции и хранение

- Запись диагностических событий не должна зависеть от успешного commit бизнес-транзакции.
- Inspector не должен сам открывать/закрывать или менять транзакции вызывающего приложения.
- В MVP допускается, что событие `pending` останется в хранилище, если PHP-процесс аварийно завершился. Политика пометки таких записей как abandoned требует отдельного решения.
- Удаление/очистка не должны выполняться в синхронном пути регистрации события.

## 12. Критерии приёмки API

1. Можно зарегистрировать источник и начать событие с обязательными полями.
2. У события есть уникальный ID и корректные correlation/parent ссылки.
3. Успешная и ошибочная финализация переводят pending в соответствующий финальный статус.
4. Повторная финализация не меняет исходный результат.
5. Ошибка бизнес-операции остаётся исходной и может быть повторно выброшена вызывающим кодом.
6. При недоступности хранилища best-effort API не ломает бизнес-операцию.
7. Тела по умолчанию не сохраняются; секреты проходят sanitization до записи.
8. API работает без HTTP-запроса и не требует конкретного транспорта.
9. Не поддерживаются повторное выполнение запроса и автоматический перехват всего трафика.

## 13. Открытые вопросы перед утверждением

- Окончательный формат ID.
- Нужен ли отдельный объект `EventStartResult` или `begin()` возвращает nullable handle.
- Нужен ли публичный интерфейс для пользовательского Sanitizer.
- Как именно регистрировать источники при недоступной БД и в режиме read-only.
- Какие поля HTTP-контекста допустимы по умолчанию.
- Требуется ли отдельный API для событий, которые начинаются и заканчиваются в разных процессах (за пределами MVP).
