# Публичный API

- **Версия:** 0.2
- **Дата:** 2026-11-24
- **Статус:** первичная реализация фасада `Inspector::begin(string $sourceCode, string $operation, array $options = [])` добавлена; API ещё будет расширяться и проверяться на BitrixVM.
- **Назначение:** определить стабильный внешний интерфейс до разработки ядра.

## 1. Принципы контракта

1. Интеграция сама выполняет бизнес-операцию; Inspector только регистрирует её ход и результат.
2. Диагностическая запись не управляет выполнением бизнес-операции.
3. Сбор данных явный: только переданные вызывающим кодом значения и контекст адаптера.
4. По умолчанию сохраняются метаданные; тела запросов/ответов не записываются.
5. Публичный API не раскрывает ORM, таблицы, административные классы и детали хранилища.
6. API работает без HTTP: CLI, агенты, cron, очереди и фоновые обработчики.
7. Контракт не обещает автоматический перехват сетевого трафика.
8. Ошибка Inspector не должна становиться причиной пропуска или изменения бизнес-операции.

## 2. Публичный namespace и типы

Namespace: `CodeMatrix\IntegrationInspector\Api`.

Предлагаемые публичные типы:

- `Inspector` — статический фасад;
- `EventInput` — неизменяемое описание запускаемой операции;
- `EventHandle` — публичный интерфейс дескриптора события;
- `EventOutcome` — данные успешного результата;
- `SourceDefinition` — необязательные описательные сведения об источнике;
- `RecordingStatus` — ограниченный результат попытки регистрации;
- `FinalizeResult` — ограниченный результат финализации.

Внутренние реализации рабочего и no-op дескриптора не входят в публичный контракт.

## 3. Фасад Inspector

Реализованный на текущем этапе метод:

```php
Inspector::begin(string $sourceCode, string $operation, array $options = []): EventHandle;
Inspector::reset(): void;
```

`begin()` принимает код источника и операции, а также массив опций. Направление по умолчанию — `outgoing`. Поддерживаемые опции: `direction`, `correlationId`, `parentEventId`, `requestMetadata`, `requestPayload`, `context`, `occurredAt`. Значение `direction` — `incoming`, `outgoing` или `internal`.

`registerSource()` и `isEnabled()` пока не реализованы. Внутренний `EventService` использует `EventInput`.

### Ключевое правило begin()

`begin()` всегда возвращает `EventHandle`, в том числе если:

- модуль отключён;
- хранилище недоступно;
- входные данные не прошли проверку;
- запись события не удалась по другой внутренней причине.

В этих случаях возвращается no-op handle. Вызовы его методов безопасны и не влияют на бизнес-код.

Это принципиально важно: нельзя помещать выполнение интеграции внутрь условия `if ($handle->isRecorded())`. Диагностика не должна определять, будет ли выполнена бизнес-операция.

Пример:

```php
$event = Inspector::begin('1c', 'order.export', [
    'direction' => 'outgoing',
    'requestMetadata' => ['order_id' => 123],
]);

try {
    $result = $integration->execute();

    $event->succeed($outcome);
} catch (\\Throwable $exception) {
    $event->fail($exception);

    throw $exception;
}
```

Вызов `fail()` не заменяет и не подавляет исходное исключение. Его повторно выбрасывает вызывающий код.

## 4. EventHandle

Предлагаемый интерфейс:

```php
interface EventHandle
{
    public function getEventId(): ?string;

    public function getRecordingStatus(): RecordingStatus;

    public function succeed(?EventOutcome $outcome = null): FinalizeResult;

    public function fail(\\Throwable $exception): FinalizeResult;
}
```

- `getEventId()` возвращает ID только если событие удалось зарегистрировать.
- `getRecordingStatus()` нужен для диагностики самого Inspector, но не для ветвления бизнес-логики.
- `succeed()` и `fail()` безопасны для no-op handle.
- Повторная финализация не меняет первоначальный результат.

## 5. Источники интеграций

Источник — логическая система или канал: `1c`, `crm`, `delivery`, `payment`, `custom_api`.

В событии всегда передаётся обязательный `sourceCode`. Описательная регистрация источника необязательна:

```php
Inspector::registerSource(new SourceDefinition(
    code: '1c',
    name: 'Обмен с 1С',
    description: 'Выгрузка заказов и загрузка каталога',
));
```

Правила:

- код источника сохраняется непосредственно в событии;
- отсутствие записи в справочнике источников не мешает регистрации события;
- если описание источника не зарегистрировано, административный интерфейс показывает сам `sourceCode`;
- регистрация описания идемпотентна по `code`;
- ошибка сохранения описания источника не блокирует регистрацию событий;
- удаление описания источника не должно удалять историю событий.

Справочник источников — вспомогательная метаинформация, а не обязательная зависимость события.

## 6. EventInput

Предлагаемые поля:

| Поле | Требование | Назначение |
|---|---|---|
| `sourceCode` | обязательно | стабильный код источника |
| `operation` | обязательно | машинный код операции, например `order.export` |
| `direction` | обязательно | `incoming`, `outgoing` или `internal` |
| `correlationId` | необязательно | связывает события одной бизнес-операции |
| `parentEventId` | необязательно | ссылка на родительское событие |
| `requestMetadata` | необязательно | безопасные структурированные метаданные |
| `requestPayload` | необязательно | текстовое тело запроса; только при двойном opt-in |
| `context` | необязательно | дополнительный технический контекст |
| `occurredAt` | необязательно | время события, известное вызывающему коду |

Ограничения:

- строки не могут быть пустыми и имеют фиксированные максимальные длины;
- `sourceCode` — lowercase ASCII slug: буквы, цифры, точка, дефис и подчёркивание;
- глубина и общий размер структур ограничиваются;
- допустимы только скаляры и массивы с поддерживаемыми ключами;
- произвольные объекты, ресурсы, замыкания и PHP-сериализация не поддерживаются;
- секреты проходят Sanitizer до передачи в постоянное хранилище.

Точные пределы длины и размера фиксируются в спецификации хранения.

## 7. Идентификаторы и корреляция

- `eventId` — UUID v4, генерируется модулем через криптографически безопасный генератор случайных байтов PHP.
- `correlationId` — необязательная непрозрачная строка от вызывающего кода. Автоматически не генерируется.
- `parentEventId` — необязательный ID родительского события в формате UUID v4, не более 36 символов.
- correlation/parent ID не являются средством авторизации.
- Для parent ID не требуется обязательный внешний ключ: родитель может находиться в другом процессе или быть удалён политикой хранения.
- Для correlationId фиксируется только ограничение длины; parentEventId обязан быть UUID v4.

Дата регистрации хранится отдельно. Сортировка по времени не зависит от порядка UUID.

## 8. Жизненный цикл

Состояния:

- `pending` — событие зарегистрировано, операция выполняется;
- `success` — вызывающий код сообщил об успешном завершении;
- `error` — вызывающий код сообщил об ошибке.

Допустимые переходы:

```text
begin -> pending
pending -> success
pending -> error
```

Повторная финализация запрещена. Она возвращает `already_finalized` и не перезаписывает первый результат.

Защита от повторной финализации должна обеспечиваться атомарным условным обновлением хранилища, а не только локальным флагом PHP-объекта.

Состояния `abandoned`, `cancelled` и автоматическое восстановление зависших событий не входят в MVP.

## 9. Результат и ошибка

`EventOutcome` может содержать:

- HTTP-статус;
- безопасные метаданные ответа;
- явный response payload (только при разрешённом сохранении тел);
- краткий код результата.

Длительность измеряет сам Inspector монотонными часами процесса. Календарные отметки начала и завершения хранятся отдельно в UTC. Переданный `occurredAt` не подменяет системное время регистрации.

`fail(Throwable $exception)` сохраняет ограниченный безопасный снимок:

- класс исключения;
- сообщение после ограничения длины и санитарной обработки;
- код исключения;
- файл и строка, если это разрешено настройками;
- stack trace выключен по умолчанию; при отдельном разрешении ограничивается по размеру и проходит Sanitizer.

Объект исключения целиком, аргументы функций, локальные переменные и произвольные свойства объектов не сериализуются.

## 10. HTTP-данные и payload

HTTP — необязательный контекст, а не зависимость ядра. Тело запроса передаётся через необязательное поле `requestPayload` в EventInput, тело ответа — через `responsePayload` в EventOutcome; оба поля являются явным opt-in.

Предлагаемые поля HTTP-контекста:

- метод;
- URL без userinfo и с маскированием чувствительных query-параметров;
- заголовки после фильтрации;
- HTTP status;
- размер тела;
- тело только при включённом разрешении и явной передаче вызывающим кодом.

Правила по умолчанию:

- тела не сохраняются;
- Authorization, Proxy-Authorization, Cookie, Set-Cookie и ключи, похожие на password/token/secret/api_key, маскируются;
- перед обработкой и после sanitization действуют ограничения размера;
- неподдерживаемые типы отбрасываются;
- Sanitizer работает до записи; UI не заменяет санитаризацию на входе.

Разрешение на запись тела должно требовать одновременно глобальной настройки и явного opt-in конкретного вызова. Маскирование по именам полей не гарантирует обнаружение секретов внутри произвольного текста; это ограничение отражается в документации.

## 11. Результаты API и ошибки самого Inspector

`RecordingStatus` и `FinalizeResult` используют ограниченные коды, например:

- `recorded`;
- `disabled`;
- `invalid_input`;
- `storage_unavailable`;
- `already_finalized`;
- `not_recorded`.

Точные классы результатов и набор кодов фиксируются перед реализацией.

Политика MVP — best effort:

- сбой Inspector не выбрасывается в основной поток бизнес-операции;
- no-op handle поглощает вызовы финализации;
- ошибка Inspector не логируется через тот же Inspector;
- нельзя гарантировать запись при отказе БД, завершении процесса, OOM или фатальной ошибке PHP;
- скрытые сетевые обращения и повторные попытки интеграционного запроса запрещены.

Строгий режим, в котором сбой диагностической записи влияет на бизнес-операцию, не входит в MVP.

## 12. Асинхронные операции и транзакции

- Handle живёт в пределах одного PHP-процесса.
- Передача handle между процессами, сериализация и продолжение события в другом worker не входят в MVP.
- Для очередей и cron каждый процесс создаёт собственное событие; связь задаётся общим correlation ID и, при наличии, parent ID.
- Inspector не открывает, не закрывает и не меняет транзакции приложения.
- Запись через default connection может быть отменена rollback внешней транзакции. Это ограничение должно быть явно показано в документации.
- Опциональный независимый режим использует отдельное именованное соединение, настроенное администратором в `.settings.php`; модуль не изменяет этот файл.
- При включённом независимом режиме отказ отдельного соединения не вызывает скрытый fallback на default connection.
- Независимость от rollback заявляется только после прохождения отдельного интеграционного теста на целевой версии ядра и MySQL.
- Подробности и критерии проверки — в [TRANSACTION-STRATEGY.md](TRANSACTION-STRATEGY.md).
- Очистка не выполняется в синхронном пути регистрации события.

## 13. Критерии приёмки API

1. Интеграция может начать событие с обязательными полями.
2. `begin()` всегда возвращает безопасный handle.
3. Бизнес-операция выполняется одинаково при включённом и отключённом Inspector, а также при отказе хранилища.
4. У события есть уникальный ID и корректные correlation/parent ссылки.
5. Успешная и ошибочная финализация переводят pending в соответствующий статус.
6. Повторная финализация не меняет исходный результат.
7. Исходное бизнес-исключение остаётся исходным и может быть повторно выброшено.
8. Тела по умолчанию не сохраняются; секреты маскируются до записи.
9. API работает без HTTP-запроса и не требует конкретного транспорта.
10. Не поддерживаются повторное выполнение запроса и автоматический перехват всего трафика.
