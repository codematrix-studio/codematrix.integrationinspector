# Архитектура (предварительная)

- **Версия:** 0.2
- **Дата:** 2026-11-24
- **Статус:** проектное предложение, подлежит технической проверке.

## 1. Общая схема

Интеграция приложения
→ публичный API Inspector
→ нормализация события
→ санитарная обработка данных (Sanitizer)
→ Storage
→ административный интерфейс.

Диагностическая подсистема не должна владеть бизнес-логикой интеграции.

## 2. Предлагаемые подсистемы

| Подсистема | Ответственность |
|---|---|
| API / Facade | Стабильная точка входа для интеграций |
| Event | Модель, handle и жизненный цикл события |
| Source | Регистрация источников интеграций |
| Sanitizer | Маскирование и ограничение данных |
| Storage | Сохранение и чтение событий |
| Filter | Фильтрация и поиск |
| Cleanup | Удаление устаревших данных |
| Admin | Интерфейс управления и просмотра |

## 3. Публичный контракт

Проект API вынесен в [API.md](API.md). Он определяет фасад, входные данные, дескриптор события, финализацию, корреляцию, payload, ошибки и best-effort поведение.

Публичный API должен быть отделён от реализации хранилища. Классы ORM и административного интерфейса не являются частью публичного контракта.

## 5. Пространство имён

Предварительно: `CodeMatrix\\IntegrationInspector`.

Публичный фасад и DTO/Value Objects располагаются в публичном API namespace. Внутренние классы хранения и реализации не следует объявлять частью публичного контракта.

## 6. Хранилище

Предварительная логическая модель:
- `b_cmi_source` — источники интеграций;
- `b_cmi_event` — метаданные событий;
- `b_cmi_event_data` — дополнительные данные запроса/ответа.

Проект физической схемы, индексы, лимиты, retention и сценарии очистки вынесены в [DATA-MODEL.md](DATA-MODEL.md). Транзакционная семантика и опциональное именованное соединение описаны в [TRANSACTION-STRATEGY.md](TRANSACTION-STRATEGY.md). Оба документа требуют проверки на целевой версии ядра и MySQL до реализации.

## 7. Надёжность

Нужно определить и протестировать:
- best-effort поведение при ошибке записи;
- поведение при переполнении лимита;
- обработку больших payload;
- защиту от рекурсивного логирования;
- транзакционные границы;
- очистку и конкурентную запись;
- повторную финализацию и аварийно незавершённые события.

Inspector не должен управлять транзакциями вызывающего приложения. Синхронный путь регистрации события не должен запускать очистку или сетевые обращения.

## 8. Совместимость

Результаты первичной проверки и оставшиеся вопросы зафиксированы в [COMPATIBILITY.md](COMPATIBILITY.md). PHP 8.2 и MySQL 8.0 соответствуют текущим минимальным требованиям платформы, но фактическая матрица совместимости модуля не утверждена. MariaDB и PostgreSQL требуют отдельных проверок.
