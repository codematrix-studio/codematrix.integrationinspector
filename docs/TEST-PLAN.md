# План тестирования MVP

- **Версия:** 0.1
- **Дата:** 2026-11-24
- **Статус:** план частично исполнен. Unit-тесты проходят в CI на PHP 8.2–8.4; установка и реальные smoke-тесты выполнены на BitrixVM. Проверка независимой записи Inspector при rollback пройдена 2026-11-24. Полная интеграционная, security, compatibility и нагрузочная матрицы остаются открытыми.
- **Назначение:** определить проверяемые условия готовности API, хранилища, безопасности и установщика до начала реализации.

## 1. Общие правила

- Каждый критичный сценарий должен иметь автоматизированный тест, если его можно воспроизвести в тестовом окружении.
- Интеграционные проверки выполняются на реальном ядре Битрикс и MySQL, а не только на моках.
- Проверки отказов должны доказывать, что бизнес-операция не меняет поведение при сбое Inspector.
- Тесты безопасности проверяют данные именно в постоянном хранилище, а не только результат отображения в UI.
- Тестовые данные не должны содержать реальные токены, пароли, персональные или платёжные данные.
- Ни один сценарий не считается пройденным до получения проверяемого результата запуска.

## 2. Уровни тестирования

| Уровень | Что проверяем | Среда |
|---|---|---|
| Unit | DTO, валидаторы, Sanitizer, генератор ID, no-op handle, переходы состояний | Изолированные тесты PHP |
| Integration | ORM, запись/чтение, атомарная финализация, очистка, установка | Ядро Битрикс + MySQL |
| Security | Маскирование, лимиты, ACL, CSRF, XSS в выводе | Тестовый сайт Битрикс |
| Compatibility | Минимальные версии PHP/ядра/СУБД | Отдельные тестовые окружения |
| Manual acceptance | Установка, настройка, просмотр журнала и карточки | Чистый тестовый сайт |

Конкретный тестовый фреймворк и способ загрузки ядра для тестов выбрать после проверки целевой версии Битрикс и доступной инфраструктуры.

Пошаговый протокол и результаты приведены в [TRANSACTION-STRATEGY.md](TRANSACTION-STRATEGY.md) и [TRANSACTION-SPIKE.md](TRANSACTION-SPIKE.md). 2026-11-24 на BitrixVM выполнен реальный smoke-тест Inspector: `inspector_storage` и `default` подключены к одной БД `sitemanager`; `Inspector::begin()` создал событие со статусом `recorded`; перед rollback событие имело `success` через оба соединения; после rollback default connection событие осталось `success` и доступным через оба соединения. Бизнес-транзакция успешно откатилась, настройка восстановлена. Окружение: CentOS Stream 9, PHP 8.2.30, MySQL 8.0.44; версия ядра Bitrix не зафиксирована. Это подтверждает независимость транзакционных сессий, но не работу с отдельной физической БД. Проверки блокировок, CLI/cron, ORM и минимальной версии ядра остаются открытыми. Ранее выполненный отдельный smoke-тест подтвердил, что запись через default connection откатывается вместе с бизнес-транзакцией.

Нормализация GET-параметров в административной странице также реализована; отдельный интеграционный тест страницы ещё не добавлен. Навигация пагинации ограничена первой, последней и пятью страницами вокруг текущей; сценарий ADM-014 реализован, но ещё не проверен вручную на BitrixVM.

## 10. Критерии допуска к альфе

Альфа может быть объявлена только после того, как:

1. Работают API-001—API-011.
2. Пройдены базовые SRC/IN сценарии.
3. Пройдены SEC-001—SEC-012, особенно маскирование до записи и ACL.
4. Подтверждены DB-001, DB-005—DB-009.
5. Установка/удаление проверены на тестовом сайте.
6. Есть воспроизводимый пример интеграции и инструкция запуска.
7. Ограничения и известные проблемы перечислены в документации.

Публичный MVP дополнительно требует прохождения полного тестового набора, проверки целевой матрицы совместимости и ручной приёмки административного интерфейса.

## 11. Правило отчётности

В статусе тестирования указывать отдельно:

- **не реализован** — теста/функции ещё нет;
- **не запускался** — тест подготовлен, но не выполнялся;
- **пройден** — есть результат успешного запуска;
- **провален** — есть воспроизводимый дефект и ссылка на задачу/исправление.

Нельзя отмечать сценарий пройденным только по просмотру кода или документации.
