# План тестирования MVP

- **Версия:** 0.1
- **Дата:** 2026-11-24
- **Статус:** проект тестовой стратегии; тесты ещё не реализованы и не запускались.
- **Назначение:** определить проверяемые условия готовности API, хранилища, безопасности и установщика до начала реализации.

## 1. Общие правила

- Каждый критичный сценарий должен иметь автоматизированный тест, если его можно воспроизвести в тестовом окружении.
- Интеграционные проверки выполняются на реальном ядре Битрикс и MySQL, а не только на моках.
- Проверки отказов должны доказывать, что бизнес-операция не меняет поведение при сбое Inspector.
- Тесты безопасности проверяют данные именно в постоянном хранилище, а не только результат отображения в UI.
- Тестовые данные не должны содержать реальные токены, пароли, персональные или платёжные данные.
- Ни один сценарий не считается пройденным до получения проверяемого результата запуска.

## 2. Уровни тестирования

| Уровень | Что проверяем | Среда |
|---|---|---|
| Unit | DTO, валидаторы, Sanitizer, генератор ID, no-op handle, переходы состояний | Изолированные тесты PHP |
| Integration | ORM, запись/чтение, атомарная финализация, очистка, установка | Ядро Битрикс + MySQL |
| Security | Маскирование, лимиты, ACL, CSRF, XSS в выводе | Тестовый сайт Битрикс |
| Compatibility | Минимальные версии PHP/ядра/СУБД | Отдельные тестовые окружения |
| Manual acceptance | Установка, настройка, просмотр журнала и карточки | Чистый тестовый сайт |

Конкретный тестовый фреймворк и способ загрузки ядра для тестов выбрать после проверки целевой версии Битрикс и доступной инфраструктуры.

## 3. API и жизненный цикл

| ID | Сценарий | Ожидаемый результат |
|---|---|---|
| API-001 | Начало события с валидными обязательными полями | Возвращён рабочий handle, событие имеет UUID v4 и статус pending |
| API-002 | Inspector отключён | Возвращён no-op handle; бизнес-код продолжает выполнение |
| API-003 | База недоступна в begin() | Возвращён no-op handle со статусом storage_unavailable; исключение не выходит в бизнес-код |
| API-004 | Некорректный EventInput | Возвращён no-op handle со статусом invalid_input |
| API-005 | Успешная финализация | pending атомарно переходит в success |
| API-006 | Ошибочная финализация | pending атомарно переходит в error; исходное исключение не изменяется |
| API-007 | Повторный succeed() | Первоначальный результат не перезаписан; возвращён already_finalized |
| API-008 | Повторный fail() после success | Статус и данные success не перезаписаны |
| API-009 | Два конкурентных вызова финализации | Только один вызов фиксирует переход из pending |
| API-010 | No-op handle получает succeed()/fail() | Нет исключения и побочных действий |
| API-011 | CLI/cron без HTTP-контекста | Событие регистрируется корректно |
| API-012 | correlationId и parentEventId | Значения сохраняются и позволяют найти связанную цепочку |

## 4. Источники и входные данные

| ID | Сценарий | Ожидаемый результат |
|---|---|---|
| SRC-001 | Регистрация нового источника | Справочник содержит код и описание |
| SRC-002 | Повторная регистрация того же кода | Нет дубликата; допустимые описательные поля обновлены |
| SRC-003 | Событие от незарегистрированного источника | Событие записано; UI использует sourceCode как имя |
| SRC-004 | Ошибка записи описания источника | Регистрация события не блокируется |
| IN-001 | Пустой sourceCode или operation | Вход отклонён безопасным результатом |
| IN-002 | sourceCode с запрещёнными символами | Вход отклонён |
| IN-003 | Слишком длинные строки | Значения отклонены/ограничены по спецификации; неконтролируемая обрезка не допускается |
| IN-004 | Объект, ресурс или замыкание в metadata | Не сериализуется; безопасный результат |
| IN-005 | Чрезмерная глубина или размер массива | Обработка останавливается в пределах лимита |

## 5. Безопасность и payload

| ID | Сценарий | Ожидаемый результат |
|---|---|---|
| SEC-001 | Authorization и Proxy-Authorization | Секреты замаскированы до записи |
| SEC-002 | Cookie и Set-Cookie | Значения замаскированы до записи |
| SEC-003 | Ключи password/token/secret/api_key | Значения маскируются согласно правилам |
| SEC-004 | Секрет находится внутри произвольного текста | Ограничение явно задокументировано; автоматическое обнаружение не обещается |
| SEC-005 | Payload передан без разрешения в настройках | Тело не сохраняется |
| SEC-006 | Разрешена настройка, но вызов не запросил payload | Тело не сохраняется |
| SEC-007 | Настройка и вызов явно разрешают payload | Сохраняется только очищенный payload в заданном лимите |
| SEC-008 | Payload превышает лимит | Запись ограничивается безопасным способом; память не расходуется на полную сериализацию огромного объекта |
| SEC-009 | Stack trace выключен | Stack trace отсутствует в хранилище |
| SEC-010 | Stack trace включён | Данные ограничены по размеру и проходят Sanitizer |
| SEC-011 | Строка содержит HTML/JS | Административный интерфейс выводит её безопасно, без исполнения |
| SEC-012 | Пользователь без прав открывает журнал/карточку | Доступ запрещён |

## 6. Хранилище и транзакции

| ID | Сценарий | Ожидаемый результат |
|---|---|---|
| DB-001 | Вставка события | Все обязательные поля сохранены |
| DB-002 | Чтение списка с фильтром даты | Используются корректные условия и индекс |
| DB-003 | Фильтр по источнику, статусу и направлению | Результаты соответствуют условиям |
| DB-004 | Поиск по correlationId | Возвращаются связанные события |
| DB-005 | Ошибка вставки event_data | Основная запись остаётся в согласованном допустимом состоянии |
| DB-006 | Ошибка обновления при финализации | Бизнес-операция не ломается; результат Inspector сообщает о сбое |
| DB-007 | Запись события внутри активной бизнес-транзакции с rollback | Диагностическая запись сохраняется независимо, если выбранная стратегия это гарантирует; иначе ограничение явно фиксируется |
| DB-008 | MySQL strict mode и utf8mb4 | Нет ошибок типов/кодировок и некорректного обрезания |
| DB-009 | Длительность | Значение рассчитано монотонными часами и не зависит от перевода системного времени |
| DB-010 | Большой объём событий | Запросы журнала остаются в приемлемых пределах; план запросов проверен через EXPLAIN |
| DB-011 | Запись через default connection внутри внешней транзакции с rollback | Запись откатывается вместе с транзакцией; это поведение явно задокументировано |
| DB-012 | Запись через отдельное именованное соединение при rollback default connection | Событие сохраняется после rollback; тест пройден на целевой версии ядра и MySQL |
| DB-013 | Независимое соединение недоступно | Нет скрытого fallback на default connection; бизнес-операция продолжает работу, Inspector возвращает безопасный результат |
| DB-014 | Проверка ORM DataManager с именованным соединением | Результаты подтверждены тестом на минимальной версии ядра; при сбое используется проверенный Storage adapter на Connection |

## 7. Очистка и жизненный цикл модуля

| ID | Сценарий | Ожидаемый результат |
|---|---|---|
| CLN-001 | Запуск очистки с истёкшим retention | Удаляются только просроченные события |
| CLN-002 | Очистка ограниченным пакетом | За запуск обрабатывается не более установленного лимита |
| CLN-003 | Повторный запуск | Нет ошибок и дублирующих побочных действий |
| CLN-004 | Параллельные запуски очистки | Нет конфликтующего удаления и повреждения данных |
| CLN-005 | Ошибка удаления event_data | Основная запись не теряется в неконтролируемом состоянии; следующий запуск может продолжить |
| INS-001 | Установка на чистом сайте | Модуль регистрируется, таблицы и права создаются |
| INS-002 | Повторное выполнение шага установки | Нет дублирования схемы или потери данных |
| INS-003 | Обновление версии модуля | Схема обновляется без потери существующих событий |
| INS-004 | Удаление с сохранением данных | Код модуля удалён, история остаётся доступной для осознанного восстановления/экспорта |
| INS-005 | Полное удаление с подтверждением | Таблицы удалены только после явного подтверждения |

## 8. Матрица окружений

До объявления совместимости необходимо заполнить и реально прогнать матрицу:

| Компонент | Целевой вариант | Статус |
|---|---|---|
| PHP | 8.2+ | Требование платформы предварительно проверено; тестов модуля нет |
| База данных | MySQL 8.0+ | Требование платформы предварительно проверено; тестов модуля нет |
| Ядро Битрикс | Минимальная поддерживаемая версия будет выбрана после технического spike | Не определено |
| MariaDB | Отдельная версия и тестовая матрица | Не заявлена |
| PostgreSQL | В MVP не заявляется | Не заявлена |
| PHP CLI / cron | Целевое окружение сайта | Не проверено |

## 9. Критерии допуска к альфе

Альфа может быть объявлена только после того, как:

1. Работают API-001—API-011.
2. Пройдены базовые SRC/IN сценарии.
3. Пройдены SEC-001—SEC-012, особенно маскирование до записи и ACL.
4. Подтверждены DB-001, DB-005—DB-009.
5. Установка/удаление проверены на тестовом сайте.
6. Есть воспроизводимый пример интеграции и инструкция запуска.
7. Ограничения и известные проблемы перечислены в документации.

Публичный MVP дополнительно требует прохождения полного тестового набора, проверки целевой матрицы совместимости и ручной приёмки административного интерфейса.

## 10. Правило отчётности

В статусе тестирования указывать отдельно:

- **не реализован** — теста/функции ещё нет;
- **не запускался** — тест подготовлен, но не выполнялся;
- **пройден** — есть результат успешного запуска;
- **провален** — есть воспроизводимый дефект и ссылка на задачу/исправление.

Нельзя отмечать сценарий пройденным только по просмотру кода или документации.
