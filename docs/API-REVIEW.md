# Ревизия публичного API

- **Версия:** 0.1
- **Дата:** 2026-11-24
- **Статус:** технические рекомендации; требуют фиксации в API.md после согласования.
- **Назначение:** убрать неоднозначности текущего проекта API до утверждения публичного контракта.

## 1. Главная проблема текущего варианта

В текущем примере вызывающий код проверяет `$start->isRecorded()` и только после этого выполняет бизнес-операцию. Это связывает выполнение интеграции с доступностью диагностического хранилища. При ошибке записи разработчик рискует случайно пропустить саму интеграцию или вынужден дублировать бизнес-код вне условия.

Для best-effort инструмента это неправильная точка зависимости.

## 2. Рекомендуемое решение: всегда возвращать EventHandle

`Inspector::begin()` должен возвращать объект `EventHandle` при любом штатно обрабатываемом исходе:

- запись началась успешно — рабочий handle;
- модуль выключен — no-op handle;
- хранилище недоступно — no-op handle;
- входные данные не прошли проверку — no-op handle с диагностическим статусом.

Вызовы `succeed()` и `fail()` на no-op handle безопасны и ничего не меняют. Они не выбрасывают исключения в бизнес-поток.

Таким образом, интеграционный код остаётся линейным:

```php
$event = Inspector::begin($input);

try {
    $result = $integration->execute();

    $event->succeed($outcome);
} catch (\\Throwable $exception) {
    $event->fail($exception);

    throw $exception;
}
```

Проверка того, удалось ли записать событие, нужна только для диагностики самого Inspector, а не для управления бизнес-операцией.

### Предлагаемый контракт EventHandle

- `getEventId(): ?string` — ID записанного события либо null.
- `getRecordingStatus(): RecordingStatus` — результат попытки регистрации.
- `succeed(?EventOutcome $outcome = null): FinalizeResult`.
- `fail(\\Throwable $exception): FinalizeResult`.

Результаты финализации ограничены фиксированными кодами, например: `recorded`, `already_finalized`, `not_recorded`, `storage_unavailable`.

Внутренняя реализация рабочего и no-op handle не является публичной частью контракта. Публичный тип может быть интерфейсом.

## 3. Валидация и ошибки

- Публичные методы Inspector не должны выбрасывать исключения из-за недоступности диагностического хранилища.
- Невалидные входные данные дают no-op handle со статусом `invalid_input`; бизнес-операция продолжает выполняться.
- Неподдерживаемые типы данных не сериализуются. Они отбрасываются с диагностическим статусом/счётчиком.
- Не перехватывать и не подавлять исключение бизнес-операции. Вызывающий код повторно выбрасывает исходный объект исключения.
- Не обещать абсолютную защиту от фатальных ошибок PHP, завершения процесса, OOM и отказа окружения.

## 4. Источники интеграций

Рекомендуется разделить идентификатор источника и его отображаемые сведения:

- `sourceCode` — обязательная строка в EventInput; например `1c`, `crm`, `delivery`.
- `registerSource(SourceDefinition)` — необязательная регистрация имени и описания для административного интерфейса.
- Событие должно сохранять `sourceCode` непосредственно, а не зависеть от существования строки в справочнике.
- Справочник источников не должен быть обязательным внешним ключом для записи события.
- Если источник ещё не зарегистрирован, событие всё равно записывается, а интерфейс показывает его code как имя по умолчанию.
- Ошибка регистрации описания источника не блокирует регистрацию события.

Такой вариант сохраняет простой API для интегратора и позволяет показывать события даже при частичной установке/сбое справочника.

## 5. Идентификаторы

Рекомендуемые правила:

- `eventId`: UUID v4, генерируется модулем через криптографически безопасный генератор случайных байтов PHP; строковое представление — lowercase с дефисами.
- `correlationId`: необязательная непрозрачная строка, которую задаёт вызывающая сторона. Не генерировать автоматически: иначе одиночный ID создаёт ложное впечатление корреляционной группы.
- `parentEventId`: необязательная непрозрачная строка. Не создавать обязательный внешний ключ: родитель может находиться в другом процессе/инсталляции или уже быть удалён политикой хранения.
- Идентификаторы корреляции не являются секретами и не участвуют в авторизации.
- Ограничить длину correlation/parent ID; точный предел зафиксировать вместе со схемой БД.

UUID v4 выбран как консервативный переносимый вариант. Сортировку по времени обеспечивать отдельным полем даты, а не порядком UUID.

## 6. Финализация и защита от повторной записи

- Допустим только переход `pending -> success` или `pending -> error`.
- Повторный вызов финализации не должен перезаписывать первое завершение.
- Защита должна обеспечиваться атомарным условным обновлением записи, а не только локальным флагом в PHP-объекте.
- `FinalizeResult` сообщает `already_finalized`, если запись уже завершена.
- Если процесс завершился до финализации, событие остаётся `pending`; политика очистки/обозначения таких событий проектируется отдельно.

## 7. Политика payload

- Метаданные и payload — разные категории данных.
- Тело запроса/ответа не сохраняется по умолчанию.
- Передача тела должна быть явной и требовать одновременного разрешения глобальной настройки и разрешения для конкретного вызова.
- Sanitizer применяется до сериализации и до передачи данных в Storage.
- Учитывать лимит размера до глубокой обработки/сериализации; затем проверять итоговый размер после sanitization.
- Не сериализовать PHP-объекты, ресурсы, замыкания и произвольные классы.
- Не обещать обнаружение всех секретов внутри свободного текста. Гарантировать маскирование известных чувствительных ключей и заголовков.
- Stack trace по умолчанию выключен. Если будет включён, ограничить длину и также пропускать через Sanitizer.

## 8. Длительность и время

- Для длительности использовать монотонные часы процесса (например, `hrtime(true)` при доступности целевой версии PHP).
- Для даты начала/завершения использовать календарное время в UTC.
- Время, переданное вызывающим кодом как `occurredAt`, хранить отдельно от системного времени регистрации; не подменять одно другим.
- Длительность вычисляется модулем, а не принимается как доверенное значение от интеграции.

## 9. Что отложить за пределы MVP

- Передача EventHandle между процессами.
- Продолжение события в другом worker.
- Публичные пользовательские плагины Sanitizer.
- Строгий режим, при котором ошибки Inspector влияют на бизнес-процесс.
- Автоматическое обнаружение всех HTTP-запросов.
- Повторное выполнение интеграционных операций.

## 10. Предлагаемый порядок утверждения

1. Утвердить поведение no-op handle и обязательность best-effort.
2. Утвердить правила источников и идентификаторов.
3. Зафиксировать DTO и сигнатуры публичных методов в API.md.
4. На основании лимитов API спроектировать физическую схему хранения и индексы.
5. После этого подготовить тест-кейсы и каркас модуля.
