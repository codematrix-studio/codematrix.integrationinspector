# Эксперимент: независимая запись при rollback

- **Версия:** 0.1
- **Дата:** 2026-11-24
- **Статус:** инструкция подготовлена; запуск на Bitrix/MySQL не выполнен.
- **Связанные документы:** [TRANSACTION-STRATEGY.md](TRANSACTION-STRATEGY.md), [TEST-PLAN.md](TEST-PLAN.md).

## Цель

Проверить на реальном ядре Bitrix, что запись через дополнительное именованное соединение к той же базе данных не откатывается вместе с транзакцией основного соединения.

Эксперимент не является частью установщика и не должен запускаться на рабочем сайте. Использовать отдельный тестовый стенд и тестовую таблицу.

## Предварительные условия

1. Отдельный тестовый сайт на минимальной поддерживаемой версии ядра.
2. MySQL той версии, которую планируется поддерживать.
3. В `.settings.php` настроено именованное соединение, например `integration_inspector_test`, с теми же параметрами БД, что и основное соединение.
4. У тестового пользователя БД есть права на создание и удаление отдельной тестовой таблицы.
5. Зафиксированы версии PHP, Bitrix, MySQL и режим автокоммита.

Модуль не должен самостоятельно редактировать `.settings.php` или создавать дополнительные подключения.

## Подготовка таблицы

Создать таблицу до начала эксперимента:

```sql
CREATE TABLE b_cmi_transaction_spike (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    marker VARCHAR(64) NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY ux_cmi_transaction_spike_marker (marker)
) ENGINE=InnoDB;
```

Использовать уникальный marker для каждого запуска. Таблица должна быть InnoDB: тест не имеет смысла на движке без транзакционной поддержки.

## Сценарий A: запись отдельным соединением переживает rollback

Выполнить в одном PHP-процессе после загрузки пролога Bitrix:

1. Получить default connection через `Application::getConnection()`.
2. Получить именованное соединение через `Application::getConnectionPool()->getConnection('integration_inspector_test')`.
3. Убедиться, что оба соединения указывают на одну и ту же тестовую базу.
4. Начать транзакцию только на default connection.
5. Через именованное соединение вставить строку с уникальным marker.
6. Выполнить rollback только на default connection.
7. Прочитать marker через default connection.
8. Ожидаемый результат: строка существует.

Схематичный фрагмент для адаптации под проверяемую версию ядра:

```php
use Bitrix\\Main\\Application;

$default = Application::getConnection();
$named = Application::getConnectionPool()
    ->getConnection('integration_inspector_test');

$marker = 'spike-' . bin2hex(random_bytes(8));

$default->startTransaction();

try {
    $named->queryExecute(
        "INSERT INTO b_cmi_transaction_spike (marker) VALUES ('"
        . $named->getSqlHelper()->forSql($marker)
        . "')"
    );

    $default->rollbackTransaction();
} catch (\\Throwable $exception) {
    if ($default->isTransactionActive()) {
        $default->rollbackTransaction();
    }

    throw $exception;
}

$result = $default->query(
    "SELECT id FROM b_cmi_transaction_spike WHERE marker = '"
    . $default->getSqlHelper()->forSql($marker)
    . "'"
)->fetch();

if (!$result) {
    throw new \\RuntimeException(
        'Named connection write did not survive default rollback'
    );
}
```

Это диагностический пример, а не готовый production-код. Перед запуском сверить наличие и сигнатуры используемых методов с минимальной версией ядра. Для теста предпочтительно применять параметризованные запросы, если выбранный API ядра их поддерживает; экранирование выше ограничено тестовым marker и не должно становиться шаблоном Storage.

## Сценарий B: запись через default connection откатывается

1. Начать транзакцию на default connection.
2. Вставить строку с другим marker через default connection.
3. Выполнить rollback.
4. Прочитать marker после rollback.
5. Ожидаемый результат: строка отсутствует.

Этот сценарий подтверждает контрольную группу и показывает, что таблица действительно транзакционная.

## Сценарий C: отказ именованного соединения

1. Настроить заведомо недоступное именованное соединение на тестовом стенде.
2. Попытаться получить соединение и выполнить тестовую запись.
3. Проверить, что запись не была незаметно выполнена через default connection.
4. Проверить, что основная бизнес-транзакция не была завершена или отменена Inspector-кодом.

Ожидаемый результат: диагностическая запись не выполнена; скрытого fallback нет; транзакция вызывающего кода остаётся под контролем вызывающего кода.

## Сценарий D: блокировки и конкурентность

1. На default connection начать транзакцию и изменить тестовую строку так, чтобы удерживать блокировку.
2. С именованного соединения попытаться прочитать/изменить ту же строку с ограниченным timeout.
3. Зафиксировать фактическое поведение и время ожидания.
4. Повторить без конфликтующей блокировки.

Не делать выводов о независимости только по простому INSERT: отдельно оценить влияние блокировок и таймаутов.

## Сценарий E: CLI и ORM

- Повторить сценарий A из CLI/cron-контекста без HTTP-запроса.
- Проверить, что ConnectionPool возвращает ожидаемое именованное соединение в этом контексте.
- Отдельно проверить ORM DataManager и `getConnectionName()` на минимальной версии ядра.
- Если ORM не позволяет однозначно выбрать нужное соединение, зафиксировать решение использовать Connection API внутри Storage.

## Критерий завершения

Эксперимент считается успешным только после фактического запуска сценариев A–E и сохранения версий окружения, вывода и обнаруженных ограничений. До этого в README и документации нельзя обещать, что отдельное соединение гарантированно сохраняет событие при rollback.

После выполнения удалить тестовую таблицу:

```sql
DROP TABLE b_cmi_transaction_spike;
```
