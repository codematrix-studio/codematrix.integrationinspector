# Установка, обновление и удаление

- **Версия:** 0.1
- **Дата:** 2026-11-24
- **Статус:** первичный установщик и создание схемы реализованы; защита административного файла от перезаписи добавлена; MigrationRunner подключён к первичной установке; добавлен исходник updater.php для пакета 0.1.1. Сборка архива и повторные VM-проверки ещё впереди.

## 1. Идентификатор и размещение

- ID модуля: codematrix.integrationinspector.
- Каталог исходников: local/modules/codematrix.integrationinspector/.
- Файл установщика: install/index.php.
- Версия пакета: install/version.php.
- Точка подключения: include.php.
- Административные страницы размещаются в каталоге модуля; копируется только адресный wrapper в /bitrix/admin. Перед копированием проверяется конфликт имени: существующий файл без маркера владения не перезаписывается. Wrapper с маркером CodeMatrix обновляется при установке новой версии; legacy-копия исходного файла также распознаётся. При удалении удаляется только файл с маркером владения или точная legacy-копия.

Bitrix обнаруживает модуль через install/index.php; класс установщика наследуется от CModule, а его имя формируется из ID модуля с заменой точки на подчёркивание. Регистрация/снятие регистрации выполняется штатным ModuleManager. Версия пакета хранится отдельно в install/version.php.

## 2. Установка

Предлагаемая последовательность:

1. Проверить наличие обязательных файлов, минимальные требования PHP и доступность Main module API.
2. Проверить, не установлен ли модуль.
3. Подключить миграционные классы и выполнить MigrationRunner на default connection: создать таблицу версии, получить MySQL advisory lock, затем создать начальную схему либо проверить baseline существующей схемы 0.1.0.
4. Зарегистрировать модуль штатным способом только после успешного создания схемы.
5. Создать начальные настройки и права доступа с безопасными значениями.
6. Зарегистрировать агента очистки только после успешного создания схемы.
7. Завершить установку и показать понятный результат.

Установка должна быть идемпотентной на уровне каждого шага. Если шаг завершился ошибкой, установщик не должен сообщать об успешной установке. При ошибке выполняется best-effort очистка принадлежащего модулю admin wrapper и theme assets; таблицы не удаляются. Нужно предусмотреть безопасное повторное выполнение после частично завершившейся установки.

## 3. Обновление

- Версия пакета задаётся в install/version.php.
- Версия схемы БД ведётся отдельно от версии пакета.
- Изменения физической схемы оформляются последовательными миграциями с постоянными целочисленными номерами.
- Обновление не удаляет и не пересоздаёт таблицы с данными.
- DDL выполняется отдельными запросами: транзакционный rollback не считается механизмом отката DDL в MySQL.
- Версия схемы повышается только после успешного завершения и проверки всех действий миграции.
- Повторный запуск сверяет фактические столбцы и индексы и продолжает только безопасно распознаваемые действия.
- Неизвестная или частичная схема приводит к остановке, а не к автоматическому пересозданию таблиц.
- Параллельные запуски должны быть защищены блокировкой.
- Резервное копирование базы перед обновлением рекомендуется, но модуль не должен выполнять полный backup самостоятельно.

Подробное решение описано в [SCHEMA-MIGRATIONS.md](SCHEMA-MIGRATIONS.md). MigrationRunner уже реализован и подключён к DoInstall(). Для штатного обновления 0.1.1 добавлен исходник корневого updater.php в `updates/0.1.1/`: он явно копирует `lib/Storage/` из пакета через `$updater->CopyFiles()`, затем запускает общий MigrationRunner. Инструкция сборки находится в `updates/README.md`. Сам архив обновления пока не собран и работа updater.php на BitrixVM не подтверждена; до этой проверки пакет не считается готовым к выпуску. Миграции не запускаются на обычном хите или при открытии журнала.

## 4. Удаление и сохранение данных

Политика продукта: **обычное удаление модуля сохраняет историю событий**.

Удаление должно:
- снять регистрацию модуля;
- удалить только те файлы/административные ссылки, которые принадлежат модулю;
- удалить агент очистки и собственные настройки/права, если они не нужны для восстановления;
- оставить таблицы событий и служебную таблицу версии схемы по умолчанию.

Полное удаление данных — отдельное явно подтверждаемое действие с предупреждением о необратимости. Не удалять таблицы автоматически только потому, что администратор нажал стандартную кнопку удаления модуля.

Если стандартный интерфейс установщика не позволяет корректно выразить два режима удаления, реализовать отдельный экран/шаг подтверждения в рамках штатного механизма Bitrix. Конкретный UX проверить на целевой версии ядра.

## 5. Безопасность установщика

- Не менять /bitrix/.settings.php, dbconn.php, системные подключения и реквизиты БД.
- Не создавать дополнительных DB-пользователей и баз.
- Не удалять общие каталоги и файлы, которые могли быть созданы другими модулями.
- Не выполнять SQL из непроверенных входных параметров.
- Не считать существование таблицы доказательством корректной схемы: сверять нужные колонки и индексы.
- Все разрушительные действия требуют явного подтверждения.
- Ошибка установки должна оставлять понятный диагностический след, не содержащий паролей/секретов.

## 6. Обязательные проверки

- [ ] Установка на чистом тестовом сайте.
- [ ] Повторный запуск после искусственного сбоя на каждом шаге.
- [ ] Установка при уже существующих таблицах с корректной схемой.
- [ ] Отказ при конфликтующей/неполной схеме без потери данных.
- [ ] Обновление между двумя версиями схемы.
- [ ] Обычное удаление с сохранением таблиц и версии схемы.
- [ ] Полное удаление только после отдельного подтверждения.
- [x] Admin wrapper не перезаписывает существующий файл с чужим содержимым; собственный wrapper обновляется по маркеру владения, legacy-копия распознаётся при удалении.
- [ ] Удаляются только собственные файлы, агенты, права и ссылки.
- [ ] Установка/обновление не меняют системные DB connection settings.
- [ ] Проверка baseline для существующей схемы 0.1.0 без служебной таблицы версии.
- [ ] Повтор миграции после частичного DDL и защита от параллельного запуска.

## 7. Именованное соединение для независимой диагностики

Модуль не должен редактировать .settings.php и не должен автоматически создавать соединение. При желании администратора отдельное соединение с именем, выбранным в настройках модуля, настраивается вручную в конфигурации Bitrix и указывает на ту же базу данных с отдельной сессией. Без такой настройки модуль использует default connection и не обещает сохранение событий при rollback внешней транзакции. Подробности — в TRANSACTION-STRATEGY.md.
