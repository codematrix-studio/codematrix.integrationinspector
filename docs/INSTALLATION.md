# Установка, обновление и удаление

- **Версия:** 0.1
- **Дата:** 2026-11-24
- **Статус:** первичный установщик и создание схемы реализованы; проверки на целевом BitrixVM ещё не выполнены.

## 1. Идентификатор и размещение

- ID модуля: `codematrix.integrationinspector`.
- Каталог исходников: `local/modules/codematrix.integrationinspector/`.
- Файл установщика: `install/index.php`.
- Версия пакета: `install/version.php`.
- Точка подключения: `include.php`.
- Административные страницы размещаются в каталоге модуля; копирование файлов в общие системные каталоги должно быть минимальным и строго адресным.

Bitrix обнаруживает модуль через `install/index.php`; класс установщика наследуется от `CModule`, а его имя формируется из ID модуля с заменой точки на подчёркивание. Регистрация/снятие регистрации выполняется штатным ModuleManager. Версия хранится отдельно в `install/version.php`.

## 2. Установка

Предлагаемая последовательность:

1. Проверить наличие обязательных файлов, минимальные требования PHP и доступность Main module API.
2. Проверить, не установлен ли модуль.
3. Подключить autoload модуля и создать таблицы/индексы через SchemaInstaller на default connection.
4. Зарегистрировать модуль штатным способом только после успешного создания схемы.
5. Создать начальные настройки и права доступа с безопасными значениями.
6. Зарегистрировать агента очистки только после успешного создания схемы.
7. Завершить установку и показать понятный результат.

Установка должна быть идемпотентной на уровне каждого шага. Если шаг завершился ошибкой, установщик не должен сообщать об успешной установке. Нужно предусмотреть безопасное повторное выполнение после частично завершившейся установки.

## 3. Обновление

- Версия модуля задаётся в `install/version.php`.
- Изменения схемы оформляются последовательными upgrade steps с идентификаторами версий.
- Обновление не удаляет и не пересоздаёт таблицы с данными.
- DDL и миграции проверяются на целевой MySQL до выпуска.
- Каждый upgrade step должен быть повторяемым либо иметь явную проверку уже применённого состояния.
- Резервное копирование базы перед обновлением рекомендуется, но модуль не должен выполнять полный backup самостоятельно.

## 4. Удаление и сохранение данных

Политика продукта: **обычное удаление модуля сохраняет историю событий**.

Удаление должно:
- снять регистрацию модуля;
- удалить только те файлы/административные ссылки, которые принадлежат модулю;
- удалить агент очистки и собственные настройки/права, если они не нужны для восстановления;
- оставить таблицы и записи событий по умолчанию.

Полное удаление данных — отдельное явно подтверждаемое действие с предупреждением о необратимости. Не удалять таблицы автоматически только потому, что администратор нажал стандартную кнопку удаления модуля.

Если стандартный интерфейс установщика не позволяет корректно выразить два режима удаления, реализовать отдельный экран/шаг подтверждения в рамках штатного механизма Bitrix. Конкретный UX проверить на целевой версии ядра.

## 5. Безопасность установщика

- Не менять `/bitrix/.settings.php`, `dbconn.php`, системные подключения и реквизиты БД.
- Не создавать дополнительных DB-пользователей и баз.
- Не удалять общие каталоги и файлы, которые могли быть созданы другими модулями.
- Не выполнять SQL из непроверенных входных параметров.
- Не считать существование таблицы доказательством корректной схемы: сверять нужные колонки и индексы.
- Все разрушительные действия требуют явного подтверждения.
- Ошибка установки должна оставлять понятный диагностический след, не содержащий паролей/секретов.

## 6. Обязательные проверки

- [ ] Установка на чистом тестовом сайте.
- [ ] Повторный запуск после искусственного сбоя на каждом шаге.
- [ ] Установка при уже существующих таблицах с корректной схемой.
- [ ] Отказ при конфликтующей/неполной схеме без потери данных.
- [ ] Обновление между двумя версиями схемы.
- [ ] Обычное удаление с сохранением таблиц.
- [ ] Полное удаление только после отдельного подтверждения.
- [ ] Удаляются только собственные файлы, агенты, права и ссылки.
- [ ] Установка/обновление не меняют системные DB connection settings.

## 7. Именованное соединение для независимой диагностики

Модуль не должен редактировать `.settings.php` и не должен автоматически создавать соединение. При желании администратора отдельное соединение с именем, выбранным в настройках модуля, настраивается вручную в конфигурации Bitrix и указывает на ту же базу данных с отдельной сессией. Без такой настройки модуль использует default connection и не обещает сохранение событий при rollback внешней транзакции. Подробности — в [TRANSACTION-STRATEGY.md](TRANSACTION-STRATEGY.md).
