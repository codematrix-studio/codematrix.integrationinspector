# Установка, обновление и удаление

- **Версия:** 0.1
- **Дата:** 2026-11-24
- **Статус:** установщик и мигратор реализованы; пакет обновления 0.1.1 собирается скриптом и проверяется GitHub Actions. Полный lifecycle установки/обновления на BitrixVM требует отдельной ручной проверки.

## 1. Идентификатор и размещение

- ID модуля: codematrix.integrationinspector.
- Каталог исходников: `local/modules/codematrix.integrationinspector/`.
- Файл установщика: `install/index.php`.
- Версия пакета: `install/version.php`.
- Точка подключения: `include.php`.
- Административные страницы размещаются в каталоге модуля; копируется только адресный wrapper в `/bitrix/admin`. Перед копированием проверяется конфликт имени: существующий файл с посторонним содержимым не перезаписывается. Wrapper с маркером владения и известная legacy-копия распознаются отдельно.

Bitrix обнаруживает модуль через `install/index.php`; класс установщика наследуется от `CModule`, а его имя формируется из ID модуля с заменой точки на подчёркивание. Регистрация выполняется штатным `RegisterModule()` только после успешного выполнения мигратора.

## 2. Установка

Установщик подключает миграционные классы напрямую из `local/modules`, выполняет `MigrationRunner` на default connection, затем регистрирует модуль, подключает автозагрузку классов, устанавливает административный wrapper и theme assets. Файлы темы устанавливаются по одному: существующий файл допускается только при полном совпадении с поставляемым; чужой или изменённый файл не перезаписывается.

При ошибке установщик сообщает её через Application, снимает регистрацию только если модуль не был установлен до начала текущей попытки, и откатывает только административный wrapper и theme assets, созданные текущей попыткой. Ошибка повторной установки не снимает регистрацию ранее установленного модуля. Ранее существовавшие ресурсы не удаляются. Таблицы и данные не удаляются. Повторную установку после частичного сбоя следует выполнять после проверки состояния схемы.

## 3. Обновление 0.1.1

Сборка штатного пакета выполняется из корня репозитория:

```bash
bash scripts/build-update.sh 0.1.1
```

Скрипт создаёт `dist/0.1.1.zip`: содержимое каталога модуля помещается в корень архива, к нему добавляются корневые `updater.php` и `description.ru`. Скрипт проверяет версию, наличие миграционных файлов, целостность ZIP и обязательные пути.

GitHub Actions собирает пакет при push, pull request и ручном запуске workflow; архив доступен в artifacts соответствующего запуска 14 дней. Автоматической публикации на сервер обновлений или создания GitHub Release нет.

Bitrix запускает корневой updater до копирования остальных файлов. Поэтому updater сначала проверяет наличие исходного каталога миграций в распакованном пакете, копирует `lib/Storage/` через штатный `$updater->CopyFiles()`, проверяет успешность копирования и побайтовое совпадение SHA-256 обязательных файлов с пакетом, затем запускает MigrationRunner. Это исключает продолжение обновления на старых файлах при неудачном или пропущенном копировании. После успешной миграции Bitrix продолжает стандартное копирование оставшихся файлов. Неустановленный модуль пропускается; при ошибке updater возвращает `$errorMessage` и пишет техническую причину в PHP error log.

CI подтверждает синтаксис, unit-тесты и структуру ZIP, но не заменяет проверку lifecycle на целевой BitrixVM. До публикации необходимо вручную проверить обновление установленной версии 0.1.0 до 0.1.1, включая baseline существующей схемы и сценарий отказа при несовпадении схемы.

## 4. Удаление и сохранение данных

Обычное удаление модуля снимает регистрацию, удаляет принадлежащий ему административный wrapper и только те theme assets, содержимое которых всё ещё полностью совпадает с поставляемыми файлами. Изменённые администратором ресурсы и чужие файлы сохраняются. Таблицы событий и служебная таблица версии схемы сохраняются. Полное удаление данных не выполняется стандартным удалением модуля.

## 5. Безопасность

- Не менять `/bitrix/.settings.php`, `dbconn.php`, системные подключения и реквизиты БД.
- Не создавать дополнительных DB-пользователей и баз.
- Не удалять общие каталоги и файлы других модулей.
- Не выполнять SQL из непроверенных входных параметров.
- Не считать существование таблицы доказательством корректной схемы: сверять столбцы и индексы.
- Все разрушительные действия требуют отдельного явного подтверждения.
- Ошибка установки/обновления не должна раскрывать пароли и секреты.

## 6. Обязательные проверки BitrixVM

- [ ] Установка на чистом тестовом сайте.
- [ ] Повторный запуск после искусственного сбоя установки.
- [ ] Установка при уже существующих таблицах с корректной схемой.
- [ ] Отказ при конфликтующей/неполной схеме без потери данных.
- [ ] Обновление установленной версии 0.1.0 до 0.1.1 штатным механизмом Bitrix.
- [ ] Проверка baseline для существующей схемы 0.1.0 без служебной таблицы версии.
- [ ] Повтор миграции после частичного DDL и защита от параллельного запуска.
- [ ] Обычное удаление с сохранением таблиц и версии схемы.
- [ ] Проверка, что установка/обновление не меняют системные DB connection settings.
- [ ] Проверка menu, иконок и административного журнала после обновления.

## 7. Именованное соединение для независимой диагностики

Модуль не редактирует `.settings.php` и не создаёт соединение автоматически. При необходимости администратор вручную настраивает отдельное именованное соединение к той же БД с отдельной сессией. Без такой настройки модуль использует default connection и не обещает сохранение событий после rollback внешней транзакции. Подробности — в [TRANSACTION-STRATEGY.md](TRANSACTION-STRATEGY.md).
