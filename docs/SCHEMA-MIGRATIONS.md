# Версионирование схемы БД

- **Статус:** проект решения; код мигратора ещё не реализован.
- **Дата:** 2026-11-24
- **Область:** таблицы и индексы CodeMatrix Integration Inspector.
- **Важно:** версия модуля и версия схемы БД — разные сущности.

## 1. Зачем это нужно

Текущий SchemaInstaller использует CREATE TABLE IF NOT EXISTS. Это делает первичное создание таблиц повторяемым, но не меняет уже существующие таблицы: добавленный в исходный DDL столбец или индекс не появится у действующей установки.

Обновление схемы должно выполняться отдельными последовательными миграциями. Нельзя считать успешный CREATE TABLE IF NOT EXISTS доказательством того, что существующая схема соответствует текущему коду.

## 2. Таблица версии

Предлагаемая служебная таблица: b_cmi_schema_version.

| Поле | Назначение |
|---|---|
| COMPONENT | Код компонента схемы; первичный ключ |
| VERSION | Последняя полностью применённая целочисленная версия |
| UPDATED_AT | Время успешного обновления версии |

Для текущего модуля используется компонент integrationinspector. Таблица служебная: обычное удаление модуля не удаляет её, как и таблицы событий.

Номер схемы увеличивается только при изменении физической структуры БД. Изменение PHP-кода или версии пакета само по себе не требует миграции.

## 3. Правила миграций

1. Миграции имеют постоянные последовательные номера: 1, 2, 3 и т. д.
2. Каждая миграция описывает одно логически связное изменение и содержит проверку исходного состояния.
3. Миграции выполняются строго по порядку; пропуск номера или неизвестная более высокая версия — ошибка.
4. Версия в b_cmi_schema_version обновляется только после успешного выполнения всех действий конкретной миграции.
5. Каждое действие повторяемо: перед добавлением столбца или индекса проверяется его фактическое наличие и характеристики.
6. Миграция не удаляет данные и не удаляет/переименовывает объекты без отдельного обоснования, теста и документированной процедуры восстановления.
7. SQL DDL выполняется отдельными запросами. Нельзя полагаться на транзакционный rollback DDL в MySQL: многие DDL-операции вызывают неявный commit.
8. Ошибка останавливает процесс. Уже выполненные DDL-операции не откатываются автоматически; повторный запуск должен безопасно продолжить работу с фактического состояния.
9. Миграции выполняются на default connection, на котором находится схема модуля. Именованное соединение для событий не используется для DDL.
10. Миграции не запускаются на каждом хите, открытии журнала или вызове публичного API.

## 4. Первичное создание и переход с текущей версии 0.1.0

Сейчас у модуля нет таблицы версии схемы, а начальная структура создаётся через SchemaInstaller. При внедрении мигратора потребуется безопасно различать три состояния.

### Новая установка

- Служебная таблица версии создаётся первой.
- Если таблиц модуля ещё нет, применяется миграция начальной схемы.
- Версия 1 записывается только после проверки таблиц, столбцов и индексов.
- Регистрация модуля выполняется после успешного завершения схемы.

### Существующая установка без таблицы версии

Это ожидаемое состояние для уже установленной версии 0.1.0.

- Мигратор проверяет фактическую структуру всех трёх таблиц: b_cmi_event, b_cmi_event_data, b_cmi_source.
- Проверяются обязательные столбцы, типы, nullability, первичные и вторичные индексы, используемые текущим кодом.
- Только полное совпадение с известной начальной схемой позволяет записать baseline version 1 без изменения таблиц.
- Если таблиц нет, установка может создать начальную схему миграцией 1.
- Если структура частичная, конфликтующая или не распознаётся, обновление останавливается с диагностикой. Нельзя автоматически пересоздавать таблицы, удалять данные или объявлять такую схему актуальной.

### Установка с частично созданной схемой

Мигратор проверяет каждый объект и может продолжить только те действия, для которых безопасно доказано ожидаемое состояние. Неизвестные расхождения приводят к остановке и ручному разбору. Наличие одноимённой таблицы само по себе не доказывает, что она принадлежит модулю.

## 5. Защита от параллельного запуска

До запуска миграций требуется получить блокировку, ограниченную текущей БД и именем модуля. Для MySQL можно рассмотреть именованную блокировку соединения через GET_LOCK с обязательным освобождением в finally.

Если блокировку получить не удалось, второй процесс не запускает DDL и сообщает, что обновление уже выполняется. Реальный способ получения/освобождения блокировки должен быть проверен на поддерживаемых версиях MySQL и Bitrix D7 Connection API до реализации.

## 6. Интеграция с жизненным циклом Bitrix

Нельзя предполагать, что произвольный метод DoUpdate() будет вызван всеми поддерживаемыми версиями установщика Bitrix. Перед внедрением необходимо проверить документированный механизм обновления модулей и фактический lifecycle на целевом ядре.

До подтверждения этого механизма:
- не запускать миграции из include.php, публичного API или административной страницы;
- не выполнять миграции незаметно в пользовательском запросе;
- не повышать версию пакета так, будто обновление схемы уже поддержано;
- сохранить отдельный проверяемый путь запуска миграций, который будет подключён к подтверждённому lifecycle после проверки.

## 7. Ошибки и диагностика

Сообщение об ошибке должно содержать текущую версию схемы, номер миграции, безопасное описание операции/объекта и рекомендацию проверить состояние схемы и повторить обновление после устранения причины.

В логах и сообщениях нельзя выводить реквизиты подключения, SQL-параметры с пользовательскими данными, payload событий или секреты.

Версия не повышается при частичном завершении миграции. Повторный запуск сначала проверяет фактическую структуру, затем безопасно продолжает либо останавливается на неизвестном состоянии.

## 8. Проверки перед выпуском

- [ ] Новая пустая БД: создаются служебная таблица, таблицы и индексы; версия 1 записана последней.
- [ ] Текущая схема 0.1.0 без таблицы версии: baseline распознаётся без изменения данных.
- [ ] Существующая схема с отсутствующим индексом: обновление не объявляет её актуальной.
- [ ] Неожиданный тип, nullable или колонка: безопасная остановка без пересоздания таблиц.
- [ ] Ошибка после одного DDL-действия: версия не повышена; повторный запуск безопасен.
- [ ] Два одновременных запуска: только один получает блокировку.
- [ ] Версия схемы выше поддерживаемой: обновление прекращается.
- [ ] Обычное удаление модуля сохраняет таблицу версии и данные событий.
- [ ] Проверены установка и обновление на BitrixVM и целевых версиях MySQL.
- [ ] Проверен подтверждённый Bitrix lifecycle обновления; миграции не стартуют на обычном хите.

## 9. Текущая схема 0.1.0

Начальная схема, которую baseline-проверка должна распознавать:

- b_cmi_event: EVENT_ID (PK), SOURCE_CODE, OPERATION, DIRECTION, STATUS, CORRELATION_ID, PARENT_EVENT_ID, DATE_START, OCCURRED_AT, DATE_FINISH, DURATION_MS, HTTP_STATUS, RESULT_CODE, ERROR_CLASS, ERROR_CODE, ERROR_MESSAGE, ERROR_FILE, ERROR_LINE.
- Индексы b_cmi_event: PRIMARY, IX_CMI_EVENT_DATE, IX_CMI_EVENT_SOURCE_DATE, IX_CMI_EVENT_STATUS_DATE, IX_CMI_EVENT_DIRECTION_DATE, IX_CMI_EVENT_CORRELATION.
- b_cmi_event_data: EVENT_ID (PK), REQUEST_META, RESPONSE_META, CONTEXT, REQUEST_PAYLOAD, RESPONSE_PAYLOAD, ERROR_TRACE.
- b_cmi_source: CODE (PK), NAME, DESCRIPTION, DATE_CREATE, DATE_UPDATE.

Точные типы, charset/collation и nullable должны сверяться с DDL в lib/Storage/SchemaInstaller.php; этот перечень не заменяет машинную проверку структуры.
