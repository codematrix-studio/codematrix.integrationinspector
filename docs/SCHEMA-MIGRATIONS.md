# Версионирование схемы БД

- **Статус:** MigrationRunner, MySQL version store, advisory lock, проверка начальной схемы и миграция v1 реализованы; runner подключён к DoInstall() и updater.php пакета 0.1.1. ZIP собирается и проверяется в CI; запуск updater на BitrixVM ещё не подтверждён.
- **Дата:** 2026-11-24
- **Область:** таблицы и индексы CodeMatrix Integration Inspector.
- **Важно:** версия модуля и версия схемы БД — разные сущности.

## 1. Зачем это нужно

`CREATE TABLE IF NOT EXISTS` делает первичное создание таблиц повторяемым, но не меняет уже существующие таблицы. Поэтому успешный DDL сам по себе не подтверждает соответствие действующей схемы текущему коду.

## 2. Таблица версии

Служебная таблица `b_cmi_schema_version` хранит компонент, последнюю полностью применённую целочисленную версию и время обновления. Для модуля используется компонент `integrationinspector`. Обычное удаление модуля не удаляет эту таблицу.

Номер схемы увеличивается только при изменении физической структуры БД. Изменение PHP-кода или версии пакета само по себе не требует миграции.

## 3. Правила миграций

1. Миграции имеют постоянные последовательные номера: 1, 2, 3 и т. д.
2. Выполняются строго по порядку; пропуск или неизвестная версия приводят к остановке.
3. Перед выполнением получается MySQL advisory lock.
4. После выполнения проверяется фактическая схема.
5. Версия фиксируется только после успешной проверки.
6. DDL выполняется отдельными запросами; rollback транзакции не считается откатом DDL.
7. Неизвестная или частичная схема не пересоздаётся автоматически.

## 4. Начальная миграция

На чистой БД создаётся начальная схема. Существующая схема 0.1.0 без записи версии принимается как baseline только после точного сравнения таблиц, колонок, типов, nullable, кодировок, collation и индексов. Несовпадение приводит к остановке без автоматического удаления или пересоздания таблиц.

## 5. Потоки запуска

- Первичная установка: `install/index.php` подключает миграционные классы из каталога `local/modules` и запускает MigrationRunner на default connection до регистрации модуля.
- Обновление 0.1.1: корневой `updater.php` сначала копирует `lib/Storage/` из пакета через `$updater->CopyFiles()`, затем запускает тот же MigrationRunner на default connection. После успеха Bitrix копирует остальные файлы пакета.
- Обычные запросы и открытие административного журнала миграции не запускают.

## 6. Сборка пакета

`bash scripts/build-update.sh 0.1.1` формирует `dist/0.1.1.zip` с содержимым модуля в корне, а также корневыми `updater.php` и `description.ru`. GitHub Actions проверяет структуру архива и прикладывает его как artifact. Это не подтверждает корректность updater в реальном Bitrix lifecycle.

## 7. Обязательная проверка перед публикацией

- [ ] Чистая БД: создаются служебная таблица, таблицы и индексы; версия 1 записана последней.
- [ ] Схема 0.1.0 без таблицы версии распознаётся как baseline без изменения данных.
- [ ] Отсутствующий индекс или неожиданный тип приводит к безопасному отказу.
- [ ] Ошибка после одного DDL-действия не повышает версию; повторный запуск безопасен.
- [ ] Два одновременных запуска: только один получает блокировку.
- [ ] Версия схемы выше поддерживаемой приводит к остановке.
- [ ] Обычное удаление сохраняет таблицу версии и данные событий.
- [ ] Обновление 0.1.0 → 0.1.1 проходит через штатный механизм Bitrix на BitrixVM.
- [ ] Проверены ошибки updater и отсутствие частичного/небезопасного копирования файлов.

## 8. Текущая схема 0.1.0

Начальная схема определяется DDL в `lib/Storage/SchemaInstaller.php`. Проверяются таблицы `b_cmi_event`, `b_cmi_event_data`, `b_cmi_source`, все их колонки, типы, nullable, charset/collation и индексы. Этот документ не заменяет машинную проверку фактической структуры.
