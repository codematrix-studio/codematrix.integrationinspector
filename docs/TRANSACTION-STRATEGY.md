# Стратегия транзакций и независимой записи

- **Версия:** 0.1
- **Дата:** 2026-11-24
- **Статус:** техническое решение для проверки; реализация отсутствует.

## 1. Проблема

Если Inspector пишет событие через то же соединение и в ту же транзакцию, что и бизнес-код, rollback может отменить диагностическую запись. Поэтому фраза «событие гарантированно переживёт rollback» недопустима без отдельного механизма и теста.

Bitrix предоставляет основное соединение и дополнительные именованные соединения через ConnectionPool. Дополнительные соединения задаются в `.settings.php`. API `ConnectionPool::getConnection($name)` возвращает соединение по имени. Для ORM существует `DataManager::getConnectionName()`, однако перед использованием ORM с именованным соединением необходим тест на минимальной целевой версии ядра. Для критического пути хранения предпочтительнее сначала проверить прямую работу через объект Connection, не обходя SQL helper и параметризацию.

## 2. Варианты

| Вариант | Поведение при rollback приложения | Сложность | Решение |
|---|---|---|---|
| A. Основное соединение | Диагностическая запись может откатиться вместе с бизнес-транзакцией | Низкая | Базовый fallback, без гарантии независимости |
| B. Отдельное именованное соединение к той же БД | Запись выполняется в отдельной транзакционной сессии и может пережить rollback основного соединения | Средняя | Предпочтительный режим независимой записи, только после проверки |
| C. Отдельная БД/внешнее хранилище | Независимость от транзакции сайта, но отдельная инфраструктура | Высокая | Не входит в MVP |
| D. Буферизация до завершения транзакции | Событие может быть записано после commit/rollback, но при аварийном завершении процесса до flush будет потеряно | Средняя | Не использовать как гарантию сохранности |

## 3. Предлагаемая политика MVP

1. По умолчанию использовать штатное соединение Bitrix, не менять транзакции приложения.
2. Не обещать сохранение события при rollback, если используется основное соединение.
3. Предусмотреть опциональное имя отдельного соединения для диагностического хранилища, задаваемое администратором в `.settings.php`.
4. Если настроено независимое соединение, Inspector использует его только после проверки доступности и схемы. Он не создаёт и не переписывает `.settings.php`.
5. Если независимое соединение не настроено, использовать default connection и явно считать режим транзакционно связанным.
6. Никакого автоматического создания второй БД, копирования паролей или редактирования системного файла конфигурации при установке.
7. В журнале/настройках показать фактический режим хранения: «основное соединение» или «отдельное соединение». Не заявлять «независимое от rollback», пока соответствующий тест не пройден.

Отдельное именованное соединение должно вести к той же БД и иметь права только на необходимые таблицы Inspector. Это не требует отдельного сервера, но требует отдельной сессии подключения. Важно: запись может блокироваться конфликтующими блокировками, недоступностью БД или ограничениями сервера. Абсолютной гарантии при отказе БД, аварии процесса или потере питания нет.

## 4. Проверка технической реализуемости

Перед выбором окончательной реализации выполнить spike:

1. На тестовом Bitrix создать дополнительное соединение с теми же реквизитами и базой, но с другим именем.
2. Начать транзакцию на default connection.
3. Через дополнительное соединение вставить тестовую строку в отдельную таблицу.
4. Выполнить rollback default connection.
5. Проверить, что строка, записанная через дополнительное соединение, осталась.
6. Повторить тест с блокировками и конкурентным чтением.
7. Проверить работу при CLI/cron.
8. Проверить ORM DataManager с `getConnectionName()` на минимальной целевой версии. Если поведение не подтверждается, использовать отдельный Storage adapter на `Connection` для всех операций хранилища.
9. Проверить, что таблицы/DDL создаются и обслуживаются через основное соединение во время установки.
10. Зафиксировать результаты с версией ядра, PHP и MySQL.

## 5. Поведение API

- `Inspector::begin()` не открывает и не завершает транзакции приложения.
- Ошибки Storage перехватываются внутри Inspector и возвращаются как RecordingStatus/FinalizeResult.
- При записи через default connection событие может быть отменено внешним rollback. Это ограничение должно быть отражено в статусе режима хранения и документации.
- При записи через независимое соединение событие должно сохраняться вне транзакции default connection, если insert успешно завершён.
- Inspector не должен автоматически переключать соединения посреди жизненного цикла одного события.
- Для одного EventHandle выбранное соединение фиксируется при begin() и используется при финализации.
- При отказе независимого соединения запрещено незаметно переключаться на default connection: это может изменить транзакционную семантику события. Возвращается безопасный no-op/ошибка записи.
- Точный способ передачи connection в Storage должен оставаться внутренней деталью.

## 6. Критерии приёмки

- [ ] rollback default connection не удаляет запись, созданную через отдельное именованное соединение.
- [ ] rollback default connection удаляет запись, созданную в той же транзакции, если это ожидаемо для базового режима.
- [ ] Inspector не меняет состояние транзакции вызывающего кода.
- [ ] Ошибка отдельного соединения не приводит к записи через default без явной политики.
- [ ] Отображаемый режим соединения соответствует фактическому.
- [ ] Поведение подтверждено на минимальной заявленной версии ядра и MySQL.
